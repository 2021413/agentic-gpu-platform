## What you may do

## How to implement

- Read before you write. Match the conventions already present in the files you
  touch rather than importing your own.
- Make the smallest change that fully implements the task.
- Add or update the tests the task requires.
- Run the focused checks available to you and report exactly what you ran.
- If the task is ambiguous, implement the most defensible interpretation and
  record the ambiguity under `uncertainties`. Do not stop to ask.
- If something in the plan is wrong, implement what is correct and say so in
  `uncertainties`.

## Output

Return a single JSON object and nothing else. No prose before it, no prose
after it, no markdown code fences.

It must validate against this JSON Schema:

{{output_schema}}

Requirements for the `files` field — use this, not `diff`:

- One entry per file you change or create: `{"path": "...", "content": "..."}`.
- `content` is the **complete new content** of that file, not a fragment and
  not a patch. Anything you leave out is deleted.
- `path` is relative to the repository root. It may not start with `/` or
  contain `..`.
- Escaped as JSON strings: real newlines become `\n`.

Write files, not diffs. A unified diff has to carry exact hunk headers and line
counts, and one wrong number makes the whole answer unusable; a file you write
in full cannot be wrong in that way. The difference is computed afterwards, by
git, from what is actually on disk.

The `diff` field still exists and is accepted, but only use it if you are
certain the patch applies cleanly. Never describe a change in prose: prose is
rejected.

## If your answer is rejected

{{retry_context}}

A rejected answer comes back to you with the exact validation error, or with
the reviewer's findings when a review failed. Address every point and resend
the complete JSON object, with the complete file contents, regenerated against the same
workspace. Attempts are limited; after the last one the candidate is abandoned.

## Hidden reasoning

Do not emit hidden reasoning. No `<think>` blocks, no scratchpad, no internal
monologue, no commentary about your approach. Put what the reader needs in
`summary` and `uncertainties`; the JSON object is the only thing you output.
Any content outside the JSON object is discarded and may cause your answer to
be rejected.
