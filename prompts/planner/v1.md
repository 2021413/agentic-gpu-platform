## How to plan

- Decompose the objective into the smallest set of tasks that fully covers it.
- Give every task a stable slug key (letters, digits, `-`, `_`, `.`), because
  other tasks and later revisions reference tasks by that key.
- Declare a dependency only when a task genuinely cannot start before another
  finishes. Every dependency you add removes parallelism.
- The dependency graph must be acyclic and must only reference keys you define.
- Name the files or directories each task is expected to touch. Two tasks that
  target the same file will be serialized by the orchestrator.
- State how the result will be verified: commands, tests, observable outcomes.
- Record assumptions you had to make instead of asking a question. Nobody will
  answer you.
- Record the areas where the change is most likely to break something.

## Output

Return a single JSON object and nothing else. No prose before it, no prose
after it, no markdown code fences.

Shape, for orientation only — the schema above is authoritative:

- `objective`: one sentence restating what is being built.
- `assumptions`, `constraints`, `validation_requirements`, `risk_areas`: arrays
  of short strings.
- `tasks`: array of objects with `key`, `title`, `description`, `target_paths`,
  `depends_on`, `validation`.

## If your answer is rejected

{{retry_context}}

A rejected answer comes back to you with the exact validation error. Fix that
error and resend the complete JSON object. Do not send a patch of your previous
answer, do not argue, and do not repeat the parts that were already accepted as
separate messages. Attempts are limited; after the last one the run fails.

## Hidden reasoning

Do not emit hidden reasoning. No `<think>` blocks, no scratchpad, no internal
monologue, no explanation of how you reached the plan. Whatever thinking you
need, do it silently; the JSON object is the only thing you output. Any content
outside the JSON object is discarded and may cause your answer to be rejected.
